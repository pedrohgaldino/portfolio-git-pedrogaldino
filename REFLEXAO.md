Minha maior dificuldade neste exercício foi o contato inicial com o terminal. Como eu nunca tinha utilizado o Git, comandos como git init, add, commit e push pareciam apenas palavras soltas, e precisei de muito esforço para entender a lógica por trás de cada um deles. No começo, me senti bastante perdido sobre qual comando deveria utilizar após o outro. Foi um aprendizado importante perceber que o Git exige um fluxo de trabalho: primeiro é preciso "avisar" a ferramenta sobre a mudança com o add para, só depois, concretizar essa alteração com um commit, que funciona como um carimbo oficial no histórico. Durante o processo, tive muito receio de alterar o código e acabar quebrando o repositório de forma irreversível. Esse medo se tornou real quando vi o primeiro erro crítico no terminal: um erro 403 (Permission Denied). Naquele momento, achei que tinha estragado o projeto permanentemente. Com a ajuda da IA, descobri que o problema era um conflito de identidade entre contas do GitHub no meu Windows. Precisei aprender a limpar as credenciais do sistema e configurar o remote set-url para que o Git reconhecesse minha conta correta. Essa experiência, apesar de estressante, foi fundamental para eu entender como o Git lida com a segurança e a autoria. Optei por fazer um código simples ("Hello World" em C++) propositalmente, para focar na aprendizagem dos requisitos mínimos da atividade e na mecânica da ferramenta. Preferi garantir a compreensão de como o Git funcionava do que me preocupar com lógica de programação complexa neste momento. Sobre os conceitos, aprendi que o commit é muito mais do que um simples "salvar". Ele é uma cópia do meu trabalho naquele exato instante. Com o uso de commits semânticos (feat, docs, fix), percebi que o histórico do projeto fica muito mais compreensível para qualquer pessoa que venha a ler o código no futuro. Já a branch me trouxe uma grande sensação de segurança; a ideia de criar uma cópia da "linha do tempo" principal para testar coisas novas sem risco de estragar a versão oficial é um recurso incrível.Por fim, os conflitos me ensinaram que o Git não falha por erro de código, mas sim quando precisa que eu tome uma decisão humana sobre qual versão manter. Resolver o conflito manualmente no VS Code, escolhendo entre as alterações de "entrada" ou as "atuais", me deu uma compreensão profunda de como o Git monitora cada linha de texto. Além disso, entendi que o Pull Request funciona como uma revisão final necessária antes de oficializar qualquer mudança na versão principal. Apesar de ainda me sentir um iniciante, a lógica de versionamento ficou clara e vejo o Git como uma ferramenta de organização essencial.
